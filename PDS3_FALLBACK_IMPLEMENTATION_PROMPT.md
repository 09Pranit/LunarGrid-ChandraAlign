# Implementation prompt: mixed PDS3/PDS4 lunar image registration

Implement a production-ready, user-selectable PDS3 label fallback for **each** source and reference image in LunarGrid Chandra-Align. A user with no separate PDS4 XML file must be able to load an `.IMG` that has an attached PDS3 label, inspect what the label actually provides, select a bounded image tile, and submit a mixed PDS3/PDS4 pair for registration. Preserve truthful provenance and quality reporting. Treat all uploaded labels, images, and paths as untrusted data.

## Repository context to verify before coding

- `app/page.tsx` exposes two image uploads and one PDS4 XML label upload with a source/reference target selector. `hooks/use-lunar-workspace.ts` currently requires either two XML labels or neither and has a 512 MiB client check. Keep the clean initial workspace and dedicated demo-load button introduced in the companion change; real uploads must never inherit sample metadata or simulated results.
- `backend/main.py` accepts `source_file`, `reference_file`, optional paired `source_label`/`reference_label`, and `params`. It parses XML through `backend/lunar_core/io/pds4_parser.py`. `backend/job_models.py` requires paired **complete** `LunarTelemetryMetadata` records. Replace this all-or-nothing assumption with explicit per-image metadata provenance and support for incomplete but valid metadata.
- `backend/pipeline.py` validates with Pillow (JPEG/PNG/TIFF/WebP/BMP only), caps images at 16,777,216 pixels and axis length below 32,767, and decodes both staged uploads with `cv2.imread`. Raw PDS3 **and** PDS4 `.IMG` files need a separate, bounded raster reader; renaming `.IMG` to `.tif` does not decode it.
- `backend/lunar_core/matching/router.py` requires GSD and incidence for both sides. It must not receive invented values. `backend/lunar_core/io/geotiff_exporter.py` may assert Moon 2000 coordinates only when a validated reference grid exists.
- Public example product `M174353756RC.IMG` has an attached PDS3 CDR label with `RECORD_BYTES=5064`, `LABEL_RECORDS=1`, `^IMAGE=2`, `LINES=52224`, `LINE_SAMPLES=5064`, `SAMPLE_BITS=16`, `SAMPLE_TYPE=LSB_INTEGER`, `SCALING_FACTOR=3.05185094759972e-05`, and signed null/saturation codes. Its image row is **10,128 bytes, spanning two 5,064-byte records**. Do not equate `RECORD_BYTES` with row stride. This label has no trustworthy GSD, incidence, sun azimuth, footprint, or map transform.
- The companion Chandrayaan-2 TMC-2 PDS4 data label describes an `UnsignedLSB2` `.img` at byte offset 0, with `148108` lines and `4000` samples (1,184,864,000 bytes), plus mission-specific geometry fields. The current 512 MiB upload and 16.7M-pixel limits reject the full scene. Do not promise direct full-scene registration without a resource-bounded tile workflow. Do not assume these two specific observations overlap.

## User behavior and precedence

1. Show a **metadata source control on each image card** with `Auto`, `PDS4 XML`, `Embedded PDS3`, and `None / image only`. `Auto` uses an explicitly supplied, valid PDS4 XML associated with that image; otherwise it detects and uses a valid attached PDS3 label; otherwise it uses image-only mode. Expose `Embedded PDS3` as a deliberate toggle even when an XML exists. Selection of one side must not change the other.
2. Show the detected standard, label location, product ID, processing level, dimensions, sample type, available geometry, missing fields, and any warnings before running. Name the state `PDS3 attached label`, `PDS4 XML`, or `No usable label`; do not describe an embedded PDS3 label as a missing XML error.
3. If a user supplied an XML that is malformed, does not describe the selected image, or conflicts with its attached PDS3 identity/dimensions, show an actionable error. Do **not** silently downgrade from a supplied invalid XML to PDS3. An explicit user switch to PDS3 may proceed only after its own validation; retain the conflict warning in the result.
4. Let either side use a different standard. An absent label on one side must not force removal of a valid label on the other. Present image-only matching as such, with reduced geometry checks and no implied map accuracy. Image-only is available for self-describing formats such as TIFF/PNG; reject raw `.IMG` without a validated label or separately supplied, validated layout.
5. Provide a bounded tile selection or validated auto-tiling path for very large rasters. Clearly show tile size, full-image pixel origin, and any derived footprint. If overlap cannot be established, request corresponding user-selected tiles or supported camera geometry; do not claim registration of the full scenes.
6. Keep the demo isolated. Loading or clearing sample data, changing a file/label/mode/tile, or starting a new job must invalidate stale previews, metrics, URLs, and exports. Make the control keyboard accessible and announce parsing and validation failures in the UI.

## PDS3 label parser: required semantics

Implement a bounded, reusable PDS3 ODL parser or use a vetted parser only after verifying its behavior against the cases below. The parser must never evaluate label text as code or fetch paths/URLs named by a label.

- Detect `PDS_VERSION_ID=PDS3` from a small initial byte window, independent of filename case. Read only a configured maximum header size (for example 1 MiB); identify the standalone `END` token **outside comments and quoted strings**. Honor `LABEL_RECORDS * RECORD_BYTES` when present and prove the header fits there. Accept CRLF/LF, padding, whitespace, `/* ... */` comments, continued quoted values, escaped quotes where ODL permits them, case-insensitive standard keywords, and namespace-style mission keywords such as `LRO:...`.
- Parse scalar strings, integers, finite decimals/exponents, radix literals, units such as `0.414400 <ms>`, ordered sequences such as `(0, 16, 69)`, and nested `OBJECT`/`GROUP` with matching `END_OBJECT`/`END_GROUP`. Keep repeated keys scoped to their object instead of overwriting them globally. Distinguish literal `NULL`, `UNK`, and `N/A` metadata sentinels from numeric pixel special constants, e.g. `OBJECT=IMAGE; NULL=-32768`. Report unsupported syntax rather than guessing.
- Validate `RECORD_TYPE`, `RECORD_BYTES`, `FILE_RECORDS`, `LABEL_RECORDS`, and `^IMAGE`. Pointers are **one-based**: record pointer `n` maps to byte `(n-1)*RECORD_BYTES`; `n <BYTES>` maps to byte `n-1`. Support attached integer/byte pointers and, if accepting detached `.LBL`, only same-upload/same-directory referenced files with explicit safe association. Reject absolute paths, parent traversal, remote URLs, ambiguous names, and unsupported includes. Never infer offset solely from text length.
- Extract the correct `OBJECT=IMAGE` and its `LINES`, `LINE_SAMPLES`, `BANDS`/band layout where present, `SAMPLE_BITS`, `SAMPLE_TYPE`, `LINE_PREFIX_BYTES`, `LINE_SUFFIX_BYTES`, scaling/offset, valid range, `NULL`, missing, and saturation codes. Compute byte counts with checked arithmetic; prove the data object and requested windows fit the actual file. Validate any mission checksum using its documented scope; never call unverified MD5 a security guarantee. Record a server-computed SHA-256 for provenance when practical.
- Decode a declared, allowlisted physical sample representation, including signed versus unsigned and little versus big endian. In particular, `LSB_INTEGER` with 16 bits is signed little-endian `int16`; `UnsignedLSB2` in the PDS4 companion is little-endian `uint16`. Add other integer/IEEE types only with tests. Packed, compressed, complex, unsupported float encodings, or unknown band interleave must fail explicitly or use a separately validated mission decoder. Do not reinterpret signed samples as unsigned or ignore line padding.
- Read only selected windows/tiles, in strips if needed. Derive line and band offsets from the object layout and pointer, **not** from `RECORD_BYTES == pixels_per_line * bytes_per_sample`. Keep raw DN/calibrated values and a separate display/matching stretch. Mask special/null/saturation codes in the raw domain before `SCALING_FACTOR` and `OFFSET`; preserve valid zero. Propagate masks through normalization, matching, interpolation, and export. Non-finite float values require explicit masking, never blanket replacement with valid zero.
- For LROC NAC, check `TARGET_NAME=MOON`, `DATA_SET_ID`, `PRODUCT_ID`, `PRODUCT_TYPE`, `FRAME_ID`, time fields, dimensions, and image object identity. Enforce consistency with the selected image and any PDS4 sidecar. Other PDS3 profiles may be supported through generic validated fields; do not make the LROC naming convention a universal PDS3 requirement.

## PDS4 and common metadata model

- Read the PDS4 `File_Area_Observational`/array descriptor as well as telemetry: bind `file_name` to the uploaded image, validate file size/checksum when requested, `offset`, axes/order, element type, scaling and special constants. Decode PDS4 `.img` windows without relying on Pillow/OpenCV. Do not run XML external entities, external DTDs, schema URLs, or network fetches from `xml-model`/`schemaLocation`; use local, pinned schemas only if schema validation is needed.
- Build a versioned common metadata record with `source_format`, product/file identity, instrument and processing level, raw raster layout, optional GSD/incidence/emission/sun azimuth/footprint/grid, units, original coordinate convention, field-level provenance, validation warnings, and a `geometry_status` such as `map_projected`, `camera_model`, or `unknown`. Missing telemetry must remain `None`, not `0`, a default average, or an estimate from summing/filename.
- Update the PDS4 parser and router contract accordingly. In particular, existing PDS4 behavior that defaults missing emission to nadir must be reviewed; do not let that value appear as measured telemetry. Preserve backward compatibility for valid existing XML uploads and API clients where feasible, with explicit versioning/migration if the request schema changes.

## Matching, geometry, and export rules

- Distinguish **metadata for pixel decoding**, **approximate acquisition/illumination metadata**, **camera geometry**, and **map georeferencing**. An attached LROC NAC CDR label can decode pixels but does not by itself locate every line on the Moon. For mission-accurate geometry, integrate a supported LROC camera model with appropriate SPICE kernels and body shape, or accept an independently validated map-projected raster/grid. USGS ISIS directs CDR/RDR NAC users to `pds2isis` rather than `lronac2isis`; `spiceinit` and `cam2map` supply the kernel-based path. Make external ISIS processing optional and explicit rather than pretending a bounding box is a geotransform.
- Normalize and record lunar coordinate frame/datum/radius, planetocentric versus planetographic latitude, positive-east versus positive-west longitude, longitude domain, projection, pixel center/corner convention, and acquisition/camera model provenance before spatial comparisons. Handle 0/360 and antimeridian crossing. A simple min/max box is only a coarse filter; use valid footprints or camera models for overlap decisions. Do not infer a north-up pixel grid from four corners of a rotated or line-scan image.
- If geometry is available for both sides, reject or flag nonoverlap and select corresponding windows at compatible map scale. If geometry is unknown on either side, permit **explicitly selected** tile pairs for image-only feature matching, report overlap as unknown, and rely on visual inspection and conservative quality gates. Do not assert that the example LROC and TMC-2 files overlap from dates or filenames.
- When both sides have trustworthy GSD and incidence, retain the current adaptive routing. Otherwise use a documented fallback matcher path or explicit engine override and mark the routing rationale `insufficient telemetry`; do not inject fabricated GSD/incidence into `route_pair`. Keep true-scale measurements and preview stretches separate. Ensure masks exclude invalid pixels from feature detection and entropy.
- Maintain full-scene-to-tile coordinate transforms for each side. State whether exported tie points are tile-local or full-scene zero-based pixel centers and include both if useful. Registered output is tied to the **reference tile**. Keep the existing held-out quality checks; report feature residuals as feature residuals, never independent lunar ground accuracy.
- Export a georeferenced Moon TIFF and latitude/longitude tie points only when the reference tile has a validated pixel-to-ground transform in the declared lunar frame. Otherwise export a plainly labeled, ungeoreferenced TIFF with empty ground-coordinate fields. Include selected metadata standard, raw product IDs, tile origins, decoded type, geometry source, missing fields, warnings, and matching mode in the dossier and UI.

## Safety and operational limits

- Stream uploads into isolated staging files with configurable per-file, aggregate, disk, memory, pixel, and worker-time quotas. Enforce limits before expensive decode and at each tile allocation. Do not simply raise the existing cap globally to accept the 1.18 GB TMC-2 image; design for deployment/proxy limits and cancel/cleanup interrupted jobs. If this deployment cannot accept full files, provide a documented local/desktop or pre-tiled ingestion route that preserves label provenance and coordinates.
- Reject truncated files, integer overflow in dimensions/offsets, impossible strides, mismatched product identities, unsupported codecs/layouts, and stale pair selections with specific errors. Keep user filenames out of filesystem paths. Prevent zip bombs if archives are ever accepted, symlink/path traversal in detached labels, unbounded XML/ODL parsing, and logs containing raw image data or credentials. Preserve existing upload and job endpoints where compatible, and run expensive parsing/decoding off the request event loop.
- Do not add large lunar raster files, private paths, credentials, or copied user data to Git. Use tiny synthetic fixtures and a small redacted/public PDS3 header fixture. Document any external tools/kernels and licenses with pinned versions; make optional geometry failures explicit.

## Tests and acceptance criteria

1. Unit tests cover ODL comments, quoted multiline text containing `END`, units, sequences, nested and repeated keys, radix numbers, unknown sentinels, one-based record/byte pointers, detached-pointer containment, size overflow, header limit, malformed nesting, and fuzz/property cases that never crash or read beyond bounds.
2. Raster tests cover signed `LSB_INTEGER` and unsigned PDS4 `UnsignedLSB2`; endianness, prefix/suffix bytes, masks and saturation codes, scaling, all-null tiles, window offsets, and a row longer than one physical record. Include a fixture matching the public `M174353756RC` header: first pixel byte at 5064, line width 5064, row width 10128, 52224 lines, `int16`, with explicit null codes. Keep tests tiny using a shortened synthetic payload rather than committing the 529 MB product.
3. API tests cover PDS4/PDS4, PDS3/PDS4, PDS4/PDS3, PDS3/PDS3, and image-only pairs; per-side Auto/forced modes; bad XML without silent downgrade; sidecar mismatches; missing optional geometry; invalid/truncated data; quota errors; cancellation cleanup; and legacy valid requests. Assert provenance is present in result reports.
4. UI tests cover both independent toggles, detected-label status, accessible error states, tile origin display, changing files or labels after a job, clean initial load, and demo mode isolation. Verify browser preview does not claim authoritative metadata before server validation.
5. End-to-end test a **known-overlap**, small mixed-standard pair for registration and artifact export. Separately test unknown/nonoverlapping geometry: registration is blocked or clearly marked image-only/review-required and no fabricated georeferencing or accuracy appears. Validate exported TIFF/CSV/report against source product IDs, tile transforms, mask behavior, and whether ground coordinates were legitimately available.
6. Benchmark bounded reads of the full-size public LROC layout and the 1.18 GB TMC-2 layout without loading entire rasters into RAM. Set and verify practical memory, upload, disk, timeout, and deployment limits. If a full-size browser upload is intentionally unsupported, the UI must direct users to the supported tile route before submission.

Deliver the implementation, migration/API notes, user-facing instructions for PDS3 and PDS4 inputs, reproducible tests, and a concise statement of remaining unsupported PDS3 layouts or geometry modes. Do not mark a mixed-standard result scientifically georeferenced without a verified camera/map transform and independent ground validation.
